So sánh bằng: === vs == vs Object.is()

Giải mã 2 thuật toán trừu tượng IsStrictlyEqual & IsLooselyEqual trong ECMA-262, làm chủ bảng quy tắc coerce của ==, và phá vỡ 3 câu hỏi phỏng vấn kinh điển nhất về NaN, null, -0.

⏳ ~15 phút · 🎯 Mục tiêu: Giải thích chính xác tại sao null >= 0 là true nhưng null == 0 lại là false, và khi nào dùng Object.is() thay vì ===.

🌍 Giải mã câu đố từ Bài 02

Cuối Bài 02, bạn đã thấy 3 biểu thức này:

JavaScript 
console.log(null > 0);   // -> false
console.log(null == 0);  // -> false
console.log(null >= 0);  // -> true  (QUÁI LẠ ?!)

Câu trả lời nằm ở chỗ >= và == thực ra là hai thuật toán trừu tượng hoàn toàn khác nhau trong ECMA-262. Bài này sẽ giải mã tận gốc.

1. Ba toán tử, ba thuật toán

JavaScript có 3 cách so sánh bằng, mỗi cái gọi vào một thuật toán trừu tượng khác nhau trong đặc tả ECMA-262:

Toán tử / Hàm Thuật toán ECMA-262 Coerce kiểu ? Điểm đặc biệt
=== IsStrictlyEqual §7.2.15 ✕ Không NaN !== NaN, +0 === -0
== IsLooselyEqual §7.2.14 ✓ Có (theo bảng quy tắc) null chỉ == undefined, không coerce trong ==
Object.is() SameValue §7.2.11 ✕ Không NaN === NaN, +0 ≠ -0 — toán học đúng nhất

2. === — IsStrictlyEqual & 2 bẫy của IEEE 754

Thuật toán IsStrictlyEqual (§7.2.15) đơn giản:

  1. Nếu typeof x ≠ typeof y → trả về false ngay lập tức.
  2. Nếu cùng type → so sánh value trực tiếp theo chuẩn IEEE 754-2019 cho số, byte-by-byte cho string.
  3. Không bao giờ thực hiện bất kỳ thao tác ép kiểu nào.
⚠️ Bẫy #1: NaN !== NaN — Số tự khác chính mình

Tiêu chuẩn IEEE 754 quy định: "Mọi phép so sánh liên quan đến NaN đều trả về false", kể cả NaN == NaN. Đây là quyết định có chủ đích — NaN đại diện cho một tập vô số giá trị "không phải số" khác nhau, chúng không thể tự bằng nhau.

JavaScript — Kiểm tra NaN đúng cách 
console.log(NaN === NaN); // false  — luôn luôn false theo IEEE 754
console.log(NaN == NaN);  // false  — cả == cũng vậy

// ❌ TRÁNH: isNaN() toàn cục ép kiểu trước khi kiểm tra -> bẫy!
console.log(isNaN("hello"));         // true  (sai! "hello" không phải NaN)
console.log(isNaN(undefined));      // true  (sai!)

// ✅ ĐÚNG: Number.isNaN() — KHÔNG coerce, chỉ true khi value thật sự là NaN
console.log(Number.isNaN("hello"));  // false (đúng!)
console.log(Number.isNaN(NaN));     // true  (đúng!)
console.log(Number.isNaN(0 / 0));   // true  (0/0 sinh ra NaN)
⚠️ Bẫy #2: +0 === -0 là true — Zero có dấu

IEEE 754 định nghĩa hai giá trị zero phân biệt: +0 và -0. Chúng có ý nghĩa khác nhau trong tính toán hướng và góc (ví dụ: 1 / +0 = Infinity nhưng 1 / -0 = -Infinity), nhưng === lại coi chúng là một.

JavaScript 
console.log(+0 === -0); // true   (=== không phân biệt)
console.log(1 / +0);    // Infinity
console.log(1 / -0);    // -Infinity  — hai giá trị KHÁC NHAU về vật lý!

3. Object.is() — SameValue: Toán học đúng nhất

Hàm Object.is() (§7.2.11) xuất hiện từ ES6, vá đúng 2 điểm lỗi của ===:

JavaScript — Object.is() sửa đúng 2 bẫy IEEE 754 
// Bẫy 1: NaN
Object.is(NaN, NaN);   // true  ✅ — toán học đúng

// Bẫy 2: -0
Object.is(+0, -0);   // false ✅ — phân biệt đúng
Object.is(+0, +0);   // true

// Các trường hợp thông thường — giống === 100%
Object.is(1, 1);       // true
Object.is("a", "a");  // true
Object.is(null, null); // true
💡 Khi nào dùng Object.is() trong thực tế ?
  • React dùng Object.is() để so sánh các phần tử trong mảng deps của useEffect, useMemo — đảm bảo NaN không trigger re-render vô tận.
  • Khi bạn cần kiểm tra chính xác -0 trong các tính toán về hướng, góc, hoặc animation.
  • Khi viết các hàm tiện ích kiểu deepEqual, shallowEqual.

4. == — IsLooselyEqual & Bảng quy tắc coerce

Đây là thuật toán phức tạp nhất. IsLooselyEqual (§7.2.14) thực hiện theo thứ tự ưu tiên:

Quy trình IsLooselyEqual(x, y) 
1. Nếu typeof x === typeof y -> dùng IsStrictlyEqual(x, y) — giống ===

2. Nếu x là null và y là undefined (hoặc ngược lại) -> return true
   (null == undefined: quy tắc đặc biệt cứng trong spec)

3. Nếu một vế là number/bigint, vế kia là string
   -> ToNumber(string) rồi so sánh lại

4. Nếu một vế là boolean
   -> ToNumber(boolean) [true->1, false->0] rồi so sánh lại

5. Nếu một vế là object, vế kia là number/string/symbol/bigint
   -> ToPrimitive(object) rồi so sánh lại

6. Các trường hợp còn lại -> return false
⚠️ Quy tắc đặc biệt quan trọng nhất: null và undefined trong ==

Bước 2 được xử lý TRƯỚC mọi bước coerce. Điều này có nghĩa là:

  • null == undefined → true (quy tắc cứng)
  • null KHÔNG bao giờ coerce sang số 0 khi dùng ==
  • → null == 0 là false, null == false là false, null == "" là false
  • null chỉ == với null hoặc undefined, không gì khác!
JavaScript — Bảng == kinh điển và giải thích từng dòng 
// ── Nhóm null / undefined (bước 2 ưu tiên) ──
null == undefined;  // true  — quy tắc cứng
null == 0;          // false — null không coerce trong ==
null == false;      // false
null == "";         // false

// ── Nhóm boolean (bước 4: ToNumber(boolean) trước) ──
"0" == false;      // true  — false->0, "0"->0, 0==0
""  == false;      // true  — false->0, ""->0, 0==0
"1" == true;       // true  — true->1, "1"->1, 1==1
"2" == true;       // false — true->1, "2"->2, 1!=2

// ── Nhóm object/array (bước 5: ToPrimitive trước) ──
[] == false;        // true  — false->0, []->""->0, 0==0
[] == 0;            // true  — []->""->0, 0==0
[] == "";           // true  — [].toString()->"", ""==""
[1] == 1;           // true  — [1]->"1"->1, 1==1

5. Giải mã hoàn chỉnh: Tại sao null >= 0 là true ?

⚡ Chìa khóa: >= và == dùng hai thuật toán KHÁC NHAU cho null

Toán tử quan hệ (>, <, >=, <=) dùng thuật toán Abstract Relational Comparison (§7.3.12), LUÔN LUÔN ép cả 2 vế về số qua ToNumber().
Toán tử == dùng IsLooselyEqual (§7.2.14) có quy tắc đặc biệt cho null.

Giải thích từng bước 
// null >= 0
// Dùng Abstract Relational Comparison:
// B1: ToNumber(null) = 0
// B2: ToNumber(0) = 0
// B3: 0 >= 0 -> true ✅
null >= 0; // true

// null > 0
// B1: ToNumber(null) = 0
// B2: 0 > 0 -> false ✅
null > 0;  // false

// null == 0
// Dùng IsLooselyEqual — bước 2 kích hoạt:
// null chỉ == null hoặc undefined, KHÔNG coerce
// -> false ✅
null == 0;  // false

// undefined >= 0
// ToNumber(undefined) = NaN
// Mọi so sánh với NaN đều false theo IEEE 754
undefined >= 0; // false
🎙️ Góc phỏng vấn Senior: 3 câu hỏi kinh điển

Câu hỏi 1: "Tại sao trong JavaScript, typeof NaN === 'number' ?"

👉 Câu trả lời Senior:
"NaN (Not-a-Number) là một giá trị đặc biệt trong chuẩn IEEE 754-2019, được phân loại vào kiểu dữ liệu số (floating-point) chứ không phải một kiểu riêng. Nó đại diện cho kết quả của các phép toán số học không xác định như 0/0, Math.sqrt(-1), hoặc parseInt('abc'). JavaScript kế thừa đúng phân loại này từ IEEE 754, vì vậy typeof NaN là 'number'."

Câu hỏi 2: "Tại sao React dùng Object.is() thay vì === để so sánh props/state ?"

👉 Câu trả lời Senior:
"React sử dụng Object.is() thông qua internal function shallowEqual vì nó xử lý đúng 2 edge case mà === sai: NaN === NaN với === là false dẫn đến state NaN sẽ trigger re-render vô tận dù giá trị không đổi, và +0 === -0 là true có thể bỏ sót sự thay đổi hướng trong animation. Object.is() giải quyết cả hai chính xác."

Câu hỏi 3: "isNaN() và Number.isNaN() khác nhau như thế nào ?"

👉 Câu trả lời Senior:
"Hàm isNaN() toàn cục (legacy) ép kiểu argument sang số qua ToNumber() trước khi kiểm tra, dẫn đến isNaN('hello') trả về true dù 'hello' rõ ràng không phải NaN. Number.isNaN() (ES6) không coerce gì cả — chỉ trả về true khi giá trị thực sự là kiểu number VÀ có giá trị NaN. Trong code hiện đại, luôn dùng Number.isNaN()."

7. Câu hỏi tư duy (Bắc cầu sang Bài 04)

Nếu bạn biết typeof null === 'object' là một lỗi lịch sử tồn tại từ 1995, thì câu hỏi đặt ra:

JavaScript 
// typeof có thực sự đáng tin cậy để kiểm tra kiểu không ?
console.log(typeof null);       // "object"  -- LỖI LỊCH SỬ!
console.log(typeof function(){}); // "function" -- nhưng function là object...
console.log(typeof []);           // "object"   -- không phân biệt được Array!

// instanceof liệu có đáng tin không ? Thử đoán kết quả:
const iframe = document.createElement('iframe');
document.body.appendChild(iframe);
const iframeArray = new iframe.contentWindow.Array();
console.log(iframeArray instanceof Array); // -> false (!) tại sao ?

👉 Tại sao instanceof thất bại khi đối tượng được tạo trong một realm khác (iframe, Worker) ? Và đâu là cách đáng tin cậy nhất để kiểm tra kiểu trong JavaScript hiện đại ?
