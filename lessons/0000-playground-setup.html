Khởi tạo sân tập JavaScript Core & Vitest Runner

Thiết lập môi trường thực thi ESM độc lập, runner kiểm thử siêu tốc và công cụ chẩn đoán V8 để không bao giờ học lý thuyết "chay".

⏱ ~10 phút · 🎯 Mục tiêu: Sân tập thực hành chạy xanh 100% test case trên máy bạn (Node 22+, Vitest 4+).

🌉 Bắc cầu: Từ lập trình ứng dụng sang mổ xẻ Core Runtime

Khi làm dự án Frontend thông thường (React/Vue/Next.js), bạn thường để các bundler như Vite/Webpack lo liệu toàn bộ cấu hình bên dưới. Nhưng trong các buổi phỏng vấn kỹ thuật cấp cao (Senior/Lead), nhà tuyển dụng sẽ yêu cầu bạn giải thích và live-coding mã nguồn JavaScript thuần (Vanilla JS), mổ xẻ từng byte trong bộ nhớ và cơ chế event loop. Bài 00 này dựng một sân tập thực chiến (Playground) độc lập giúp bạn kiểm chứng mọi giả thuyết code ngay lập tức.

1. Kiểm tra tiền đề môi trường trên máy thật

Môi trường của bạn đã có sẵn Node.js v22.22.2 và npm v11.4.2. Node 22 hỗ trợ native ECMAScript Modules (ESM), Top-level await, và các Web APIs tiêu chuẩn (như fetch, structuredClone, AbortController, queueMicrotask) mà không cần thêm bất kỳ polyfill nào.

PowerShell / Terminal — Kiểm tra phiên bản 
# Kiểm tra phiên bản Node.js và npm
node -v   # Kết quả: v22.x.x
npm -v    # Kết quả: 11.x.x

2. Cấu trúc Sân tập & Cấu hình ESM (`"type": "module"`)

Thư mục practice/ được cấu hình là một Node ESM package chuẩn mực thông qua thuộc tính "type": "module" trong package.json. Điều này cho phép chúng ta dùng cú pháp import / export tự nhiên của JavaScript hiện đại mà không cần qua trình biên dịch Babel.

JSON — practice/package.json 
{
  "name": "js-core-practice",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  },
  "devDependencies": {
    "vitest": "^4.1.11"
  }
}
💡 Vì sao chọn Vitest thay vì Jest cho khoá học này?

1. Tốc độ vượt trội: Vitest tận dụng kiến trúc biến đổi module tức thì qua worker threads của Vite, chạy test nhanh gấp 5-10 lần Jest.
2. Native ESM: Không gặp các lỗi kinh điển về biến đổi cú pháp ESM / CommonJS mà Jest thường mắc phải.
3. API tương thích 100%: Các hàm describe, it, expect hoàn toàn tương tự Jest, chuẩn mực cho mọi bài thi phỏng vấn live-coding.

3. Viết Sanity Check & Chạy thử nghiệm

File practice/sanity.test.js kiểm tra 3 điểm cốt lõi của JavaScript runtime:

JavaScript (ESM) — practice/sanity.test.js 
import { describe, it, expect } from "vitest";

describe("Sanity Check: Môi trường JavaScript Core & Vitest", () => {
  it("Kiểm tra phép toán số học cơ bản", () => {
    // Đảm bảo runtime hoạt động chuẩn xác
    expect(1 + 1).toBe(2);
  });

  it("Kiểm tra kiểu dữ liệu JavaScript Core: typeof NaN là number", () => {
    // NaN (Not-a-Number) trong chuẩn ECMA-262 vẫn mang kiểu primitive là 'number'
    expect(typeof NaN).toBe("number");
  });

  it("Kiểm tra cơ chế so sánh bằng nghiêm ngặt của Object.is", () => {
    // Object.is phân biệt được +0 và -0, và nhận diện đúng NaN === NaN
    expect(Object.is(NaN, NaN)).toBe(true);
    expect(Object.is(+0, -0)).toBe(false);
  });
});

🎙️ Góc phỏng vấn: ESM vs CommonJS & Tại sao `typeof NaN === "number"`?

Câu hỏi 1: "Tại sao trong JavaScript `typeof NaN` lại trả về `'number'` dù tên nó là Not-a-Number?"
👉 Trả lời Senior: Theo chuẩn ECMA-262 (Number type) và chuẩn số thực dấu phẩy động IEEE 754, NaN là một giá trị đặc biệt thuộc tập số thực (Floating-Point Number) dùng để biểu thị kết quả của một phép tính toán học không hợp lệ (như 0 / 0 hoặc Math.sqrt(-1)). Vì thế kiểu dữ liệu gốc (primitive type) của nó vẫn là number.

Câu hỏi 2: "Điểm khác nhau cơ bản giữa ESM (`import/export`) và CommonJS (`require/module.exports`) là gì?"
👉 Trả lời Senior: ESM phân tích tĩnh (static analysis) lúc compile time, hỗ trợ Live Bindings (tham chiếu sống động tới giá trị được export) và hỗ trợ nạp bất đồng bộ. CommonJS nạp động lúc runtime, sao chép giá trị (value copy) tại thời điểm gọi hàm và chạy đồng bộ làm block luồng.
