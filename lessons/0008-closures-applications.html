1. Các Design Patterns kinh điển ứng dụng Closures

1.1. Revealing Module Pattern (Đóng gói Private State)

Trước khi ES6 Modules (ESM) ra đời, Revealing Module Pattern là tiêu chuẩn vàng để xây dựng các thư viện độc lập. Bằng cách kết hợp hàm tạo (hoặc IIFE) với Closures, chúng ta ẩn giấu hoàn toàn dữ liệu nhạy cảm và chỉ phơi bày (reveal) các hàm API công khai :

JavaScript — Revealing Module Pattern 
function createBankVault(initialCash) {
  // BIẾN RIÊNG TƯ (Private): Không ai từ bên ngoài có thể đọc/ghi trực tiếp
  let cash = initialCash;
  const history = [];

  function record(type, amount) {
    history.push({ type, amount, at: Date.now() });
  }

  // PUBLIC API: Chỉ trả về những phương thức được phép
  return {
    deposit(amount) {
      if (amount <= 0) throw new Error("Invalid amount");
      cash += amount;
      record("DEPOSIT", amount);
      return cash;
    },
    getBalance() {
      return cash;
    }
  };
}

const vault = createBankVault(1000);
vault.deposit(500);
console.log(vault.getBalance()); // → 1500
console.log(vault.cash);          // → undefined (Tuyệt đối an toàn !)

1.2. Function Currying & Partial Application

Currying là kỹ thuật chuyển đổi một hàm nhận nhiều tham số thành một chuỗi các hàm liên tiếp, mỗi hàm chỉ nhận một tham số duy nhất. Nhờ có Closures, mỗi hàm con đều ghi nhớ các tham số ở các bước trước đó :

JavaScript — Currying & Configurable Logger 
// Cấu hình hàm Logger bằng Partial Application
const createLogger = (env) => (moduleName) => (message) => {
  console.log(`[${env}][${moduleName}]: ${message}`);
};

const prodLogger = createLogger("PROD");
const authLogger = prodLogger("AUTH");

authLogger("User logged in successfully");
// → "[PROD][AUTH]: User logged in successfully"

1.3. Memoization (Tối ưu hóa hiệu năng bằng bộ đệm Cache)

Memoization tận dụng một bảng băm (Map) nằm bên trong phạm vi Closure để lưu trữ kết quả của các hàm thuần túy (Pure Functions). Nếu tham số đầu vào đã từng được tính toán trước đó, kết quả trả về ngay lập tức với độ phức tạp O(1) :

JavaScript — Hàm Memoize vạn năng 
function memoize(fn) {
  const cache = new Map(); // Ẩn giấu an toàn trong Closure Scope

  return function (...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      return cache.get(key); // Trả về từ cache, không tốn CPU
    }
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

2. Mặt tối của Closures: 3 Kịch bản Memory Leaks kinh điển

⚠ Khi nào một biến bị coi là "Rò rỉ bộ nhớ" (Memory Leak) ?

Trong JavaScript, Garbage Collector (GC) hoạt động dựa trên thuật toán Mark-and-Sweep (Đánh dấu và quét) từ gốc Root (Global Window / Stack). Bất kỳ ô nhớ nào vẫn còn đường dẫn tham chiếu (Reference Path) nối tới Root đều được coi là "Reachable" và sẽ KHÔNG BAO GIỜ bị thu hồi, kể cả khi chương trình không còn dùng tới nó !

Kịch bản 1: Dangling Event Listeners & Detached DOM Tree

Khi bạn gắn một closure vào một DOM element, closure đó giữ tham chiếu đến scope cha. Ngược lại, nếu bạn gỡ DOM element ra khỏi màn hình (remove() hoặc trong component unmount) nhưng quên không removeEventListener, cả DOM element lẫn toàn bộ Context Object của Closure đều bị kẹt trên Heap :

JavaScript — Bug rò rỉ Detached DOM 
function attachHandler() {
  const heavyData = new Array(1_000_000).fill("Data nặng");
  const btn = document.getElementById("submit-btn");

  btn.addEventListener("click", () => {
    // Callback này giữ tham chiếu tới `heavyData` qua Closure !
    console.log(heavyData.length);
  });
}
// Khi submit-btn bị xóa khỏi DOM, nếu không removeEventListener,
// heavyData (hàng chục MB RAM) vĩnh viễn không thể thu hồi !

Kịch bản 2: Bỏ quên Timers (setInterval)

Hàm callback truyền vào setInterval sẽ được Web API giữ tham chiếu liên tục cho tới khi bạn gọi clearInterval. Nếu component đã biến mất mà timer vẫn chạy, toàn bộ biến trong closure sẽ tồn tại mãi mãi.

Kịch bản 3: Hiện tượng Shared Lexical Environment Leak (Meteor Bug)

Đây là bug rò rỉ tinh vi bậc nhất, từng làm đau đầu các kỹ sư tại Meteor Framework :

JavaScript — Rò rỉ do chia sẻ Context Object 
let globalHolder = null;

function leakScope() {
  const hugePayload = new Array(1_000_000); // Mảng siêu lớn

  function unusedClosure() {
    // Hàm này tham chiếu tới hugePayload, nhưng KHÔNG BAO GIỜ ĐƯỢC GỌI
    if (hugePayload) console.log("hi");
  }

  // Hàm này KHÔNG dùng hugePayload, nhưng được lưu vào biến toàn cục !
  globalHolder = function harmlessFunction() {
    return 42;
  };
}

setInterval(leakScope, 100); // RAM sẽ tăng liên tục không có điểm dừng !
💡 Tại sao harmlessFunction lại làm rò rỉ hugePayload ?

Như chúng ta đã biết ở Bài 07, JavaScript Engine tối ưu hóa bằng cách tạo CÙNG MỘT Context Object trên Memory Heap cho tất cả các hàm con sinh ra trong cùng một Execution Context !

Vì unusedClosure tham chiếu tới hugePayload, V8 đưa hugePayload vào Context Object đó. Khi globalHolder lưu giữ tham chiếu tới harmlessFunction, nó vô tình giữ luôn cả Context Object chứa hugePayload !

3. Kỹ thuật săn tìm Memory Leaks với Chrome DevTools Memory Profiler

Thuật ngữ DevTools Ý nghĩa kỹ thuật chính xác Tầm quan trọng khi điều tra Bug
Shallow Size Dung lượng bộ nhớ do chính bản thân đối tượng đó chiếm giữ (không tính các đối tượng con mà nó trỏ tới). Thường rất nhỏ (vài chục bytes đối với hàm hoặc object rỗng).
Retained Size Tổng dung lượng bộ nhớ sẽ được giải phóng lập tức nếu đối tượng này bị tiêu hủy (bao gồm toàn bộ cây tham chiếu phụ thuộc). Chỉ số quan trọng nhất ! Cột cần sắp xếp giảm dần để tìm ngay thủ phạm ngốn hàng chục MB RAM.
Distance Số bước (khoảng cách cạnh) trên đồ thị bộ nhớ từ GC Root đến đối tượng. Khoảng cách càng ngắn chứng tỏ đối tượng càng bám chặt vào Global Scope.
Detached Elements Các DOM Node đã bị gỡ khỏi trang web nhưng vẫn bị giữ lại bởi JavaScript variables/closures. Gõ Detached vào thanh filter của Heap Snapshot để bắt quả tang.
🔍 Quy trình 3 bước chuẩn Senior để bắt Memory Leak
  1. Snapshot 1 (Baseline): Mở DevTools → Tab Memory → Chọn Heap snapshot → Bấm Take snapshot khi ứng dụng vừa tải xong.
  2. Thực hiện hành động: Mở màn hình/modal nghi ngờ → Tương tác → Đóng/Hủy modal → Lặp lại 5-10 lần.
  3. Snapshot 2 (Comparison): Bấm nút Collect Garbage (biểu tượng thùng rác) để dọn các rác vô hại → Chụp Snapshot 2 → Chọn chế độ hiển thị Comparison (so sánh với Snapshot 1). Tìm những đối tượng có giá trị # Delta tăng đột biến !

4. Góc phỏng vấn Senior Frontend

🎓 Q1: Phân biệt Shallow Size và Retained Size trong Heap Profiling. Khi debug rò rỉ bộ nhớ, bạn quan sát cột nào ?

Trả lời Top-Down chuẩn Senior :

"Shallow Size là kích thước bộ nhớ vật lý của chính đối tượng đó, ví dụ một Function hay Object rỗng chỉ chiếm khoảng 32-64 bytes. Trong khi đó, Retained Size là tổng dung lượng bộ nhớ sẽ được Garbage Collector thu hồi nếu đối tượng đó bị giải phóng. Khi săn tìm Memory Leak, chúng ta luôn sắp xếp theo Retained Size, vì một closure chỉ có Shallow Size vài chục bytes có thể đang neo giữ một Context Object chứa cây DOM khổng lồ hay mảng dữ liệu hàng chục Megabytes."

🎓 Q2: Làm thế nào để thiết kế một Subscription/Event Pattern hoàn toàn an toàn trước Memory Leaks ?

Trả lời Top-Down chuẩn Senior :

"Một pattern đăng ký an toàn phải luôn trả về một hàm Cleanup/Unsubscribe ngay khi đăng ký. Bên trong hàm unsubscribe, ta thực hiện lọc hoặc xóa tham chiếu tới callback khỏi mảng listeners. Đồng thời trong môi trường hiện đại, chúng ta có thể sử dụng AbortController với tùy chọn { signal } trong addEventListener, hoặc tận dụng cấu trúc dữ liệu WeakMap / WeakSet để giữ tham chiếu yếu (Weak Reference) cho phép GC tự động dọn dẹp khi đối tượng không còn được sử dụng."
